# Design — UI Overhaul + Instance Detail rework

Status: **planning only (not approved, not built).** Source of truth for requirements:
`docs/handoff/ui-overhaul-brief.md` (captured 2026-06-19). Spec: `docs/spec/ui-overhaul.md`.

This is a **large, multi-workstream rework** of the launcher UI, with a small but load-bearing
backend tail (per-instance Java/RAM actually reaching the JVM; a provider pack-info fetch). It is
decomposed into independently-shippable workstreams (§7) so each can land on its own branch and ship
without waiting on the others.

---

## 1. Scope (from the brief, nothing dropped)

1. **Collapsible/interactive sidebar** — not always popped out; collapse state **persisted**; toggle
   surfaced in UI Settings.
2. **"Toggle-everything" Settings audit** — find implicit on/off UI behaviors and surface them as
   explicit Settings toggles. (Enumerated in §6.)
3. **Instance Detail rework** — keep the name/version header; **also** show the downloaded provider
   pack version; add a **tab bar** under the header: **Info** (default), **Modlist**, **Tech Info**,
   **Java**. Remove the "Manage installs" button + slide-over; replace with the full-screen Modlist
   tab.
4. **Java/RAM** — global default RAM = **4096 MB** (already the default); per-instance Java config
   (path, min/max RAM, extra args) overriding global; "use pack settings vs global" toggle on the
   Java tab; provider-recommended settings take precedence **when present** (see §5 reality check);
   Java "fully configurable on all platforms" with cross-platform **deferred** (Windows first).

## 2. Current-state ground truth (investigated, not assumed)

### 2.1 What already exists (de-risks the plan)

- **Instance data model** (`src-tauri/src/core/instances.rs:68-87`) already has: `source: Option<Source>`
  with `pack_version: String` (instances.rs:42-47); `last_played: Option<String>`;
  `total_playtime_sec: u64`; `pack_locked: bool`; and `java: JavaCfg` with
  `{ major: Option<u32>, args_override: Option<String>, memory_mb: u32 }` (instances.rs:34-38).
- **`record_playtime`** (instances.rs:217-227) already increments `total_playtime_sec` + stamps
  `last_played` on game exit; it is called from the launch monitor (`launch.rs:1025-1031`).
- **Settings** (`settings.rs:17-37`) already has `default_memory_mb` defaulting to **4096**
  (settings.rs:42-44) and `default_java_args` defaulting to `"-XX:+UseG1GC"`. The global 4 GB default
  is **already satisfied** — no change required to hit the brief's number.
- **PackSourcePanel** (`InstanceDetail.tsx:295-433`) already renders provider + project id +
  `pack_version` + version dropdown + Update + Lock/Unlock. The pack version is already captured and
  displayed; the rework relocates it into the header + Info tab rather than inventing it.
- **InstanceDetail stat grid** (`InstanceDetail.tsx:183-202`) already renders Memory, Java, mod count,
  Created, Last played, Playtime — i.e. the Tech-Info data is already surfaced, just not as a tab.
- **bindings.ts** is generated by tauri-specta (header at `src/lib/bindings.ts:1`); `ipc.ts` adapts it.
  Any Rust DTO/command/event change requires **regenerating bindings.ts** via `scripts/build.sh dev`
  on Windows (start dev window → wait for `[bindings] exported` → stop).

### 2.2 The real gaps (what this rework must actually build)

- **G1 — per-instance memory/args never reach the JVM.** `JavaCfg.memory_mb` and
  `JavaCfg.args_override` are persisted but **not used at launch**. `build_argv`/`default_jvm_args`
  (`launch.rs:362-371`) emit **no `-Xmx`/`-Xms` at all** today. The hook point is `lib.rs:840-851`
  (`app_settings` already loaded; `inst` in scope; `build_argv` at line 850).
- **G2 — no per-instance Java path.** `JavaCfg` has `major` (version) only, **no custom path**. Launch
  always calls `core::java::ensure_java(&app, launch_meta.java_major)` (`lib.rs:810`). A per-instance
  override path must be added to `JavaCfg` and honored before `ensure_java`.
- **G3 — no min-heap field.** `JavaCfg.memory_mb` is a single value (max heap). The brief wants
  min/max — needs a second field or a documented "min = max" convention.
- **G4 — no provider pack-info fetch.** The `ModProvider` trait (`providers.rs:273-292`) has only
  `search` + `get_versions`. There is **no** "get full project description/body" call. The Info tab
  needs a new provider method + Tauri command. Only a short `summary` is captured locally.
- **G5 — sidebar is fixed, store has no UI slice.** `Sidebar.tsx:92` is `w-60 shrink-0`, always open;
  the Zustand store (`store.ts`) has `tasks` + `runs` only — **no UI slice, no persistence
  middleware**. Collapse state needs a home (decision in §4.3).
- **G6 — Settings UI has no Java path field and no toggles.** `Settings.tsx` renders memory + args +
  CF key, all plain inputs; no boolean toggles at all. The "toggle-everything" audit adds the first
  ones.

### 2.3 Existing `ipc.ts` drift to fix opportunistically

The `Settings` interface consumed by the frontend is missing `offlineMode` (noted in the instances
signals). Regenerating bindings as part of WS-A will pick this up; the offline toggle (§6) consumes it.

## 4. Key design decisions

### 4.1 Effective Java/RAM resolution (the precedence rule)

Resolved at launch in a single pure helper (`resolve_effective_java`), unit-tested in the sibling
`<stem>_tests.rs`. Precedence, highest first:

1. **Provider-recommended settings** — *honored only if present.* Per §5 these are **not exposed by
   either provider format today**, so this tier is currently always empty. We still model it (a
   nullable `recommended` block on `Source`) so the tier exists and can be populated if a future
   provider/endpoint supplies it. **This is plumbing, not a feature that does anything yet.**
2. **Per-instance config** — used when the Java tab's "use pack settings (pack-specific)" toggle is
   **on**: `JavaCfg.memory_mb` (max), new min field, `args_override`, new per-instance java path.
3. **Global default** — `settings.default_memory_mb` (4096) + `settings.default_java_args` +
   `ensure_java(major)` auto-provision. Used when the toggle is off or fields are unset.

Output: `{ xmx_mb, xms_mb, extra_args: Vec<String>, java_path: Option<PathBuf> }`. `build_argv`
prepends `-Xmx{n}M -Xms{n}M` + `extra_args`; if `java_path` is `Some`, launch skips `ensure_java` and
uses it directly, else falls back to `ensure_java(major)` (current behavior).

**Naming clarification for the brief.** The brief says the Java tab toggle is "use pack settings
(pack-specific) **vs** global Java settings." We read "pack settings" = the per-instance override block
(tier 2), since true provider-recommended values (tier 1) don't exist yet. The toggle therefore
switches between **per-instance override** and **global default**. This is an open question (§8 Q4) in
case the human meant something narrower.

### 4.2 Min/max RAM modeling (G3)

Add `min_memory_mb: Option<u32>` to `JavaCfg` (keep `memory_mb` as max). When `min` is `None`, default
`-Xms` to `min(256, xmx)` or simply omit `-Xms` (decision deferred to Q5). `#[serde(default)]` keeps
old manifests loading without a schema bump (same pattern as `from_pack`/`pack_locked`).

### 4.3 Where sidebar collapse state lives (G5)

Two candidates:

- **(A) Zustand `ui` slice + `zustand/persist` (localStorage).** Pure-frontend, instant, no IPC, no
  Rust change. Best fit for ephemeral UI chrome state.
- **(B) `settings.json` via a new `Settings.sidebar_collapsed` field.** Survives across machines if data
  dir is synced; consistent with "toggle lives in Settings"; but every toggle round-trips IPC.

**Recommendation: (A) for the live collapse state, (B) for the Settings toggle that sets the
*default*.** i.e. localStorage holds the current open/closed; the Settings page exposes a "Sidebar
starts collapsed" boolean persisted in `settings.json`. This satisfies both "persisted" and "toggle in
Settings" without making every sidebar click hit disk. Flagged as Q1 since it's a real choice.

### 4.4 Tab bar / routing

Tabs implement as **nested routes** under `/instances/:slug` (`/info` default, `/modlist`, `/tech`,
`/java`) using React Router v7 nested `<Outlet>`, OR as **local `useState` tab index**. Nested routes
give deep-linking + back-button correctness and match the existing router setup; recommend nested
routes. The header (name, version, pack version, Launch/Stop) stays **outside** the `<Outlet>` so it
persists across tabs. Q2.

### 4.5 Info tab data source (G4)

The locally-stored `Source` has only `pack_version` + a short `summary` (if captured). The brief wants
the provider's pack **info/description**. Add a backend `get_pack_info(provider, project_id)` command
backed by a new `ModProvider::get_project` method:

- **Modrinth:** `GET /v2/project/{id}` → `body` (full Markdown description) + `title` + `icon_url`.
- **CurseForge:** `GET /v1/mods/{id}` → `summary`; full description via
  `GET /v1/mods/{id}/description` (HTML). Normalize to a `PackInfo { title, description_md_or_html,
  icon_url, body_is_html }` DTO.

Rendered in the Info tab. Markdown rendering needs a renderer dep (e.g. `react-markdown`) — Q3 (add
dep vs render as preformatted text first cut). Cache via TanStack Query (`["pack-info", provider, id]`).

### 4.6 Modlist tab (replace slide-over)

The slide-over's `InstalledModsTab` + `AddModTab` content moves into a full-screen Modlist tab:
- **Installed** list = the existing `folderMods` reconciliation + per-mod enable/disable/update/remove
  (already built; just relocated and given full height + scroll).
- **Add** flow = the existing provider-search `useInfiniteQuery` (`InstanceDetail.tsx:598-609`) moves
  in as an "Add mods" affordance (sub-tab or button opening an inline panel). The `SlideOver` import +
  `ManageInstallsPanel` are deleted. No backend change — pure relocation. The `pack_locked` gating
  carries over.

### 4.7 Cross-platform Java configurability (deferred)

Per-instance java path + the resolution helper are platform-agnostic Rust. The **Windows-first**
constraint applies to UI affordances like a native "Browse for java.exe" file picker and validating a
chosen binary. Plan: ship the data model + resolution + a text-input path on all platforms; a polished
file-picker + `java -version` validation is Windows-first, others deferred. Q6.

## 5. Provider-recommended settings — REALITY CHECK (flagged per brief)

**Verified against primary sources** (Modrinth + CurseForge format docs) and the actual parsers in
`core/modpack.rs`:

- **Modrinth `.mrpack` (`modrinth.index.json`)** fields: `formatVersion, game, versionId, name,
  summary (optional), files, dependencies`. **No recommended RAM, memory, or Java field. No long
  description/body** — only an optional short `summary`. (modpack.rs:148-189.)
- **CurseForge manifest.json** fields: `name, version, author, minecraft{version, modLoaders},
  files, overrides`. **No recommended RAM, memory, or Java field.** (modpack.rs:272-327.)

**Verdict:** *Provider-recommended RAM/Java is NOT reliably (in fact, not at all) exposed by either
provider's modpack format.* The "use provider-recommended settings" tier (4.1 tier 1) is therefore
**plumbing with no live data source.** Realistic behavior shipped:

- Tier 1 (recommended) is modeled as an always-`None` `recommended` block → effectively a no-op today.
- The **real** fallback the user experiences is **per-instance override (when toggle on) → global
  default 4096 MB** (tiers 2→3).
- The Info tab's description comes from the **provider project API** (a *separate* live call, §4.5),
  not from the locally-stored pack metadata.

This must be communicated honestly in the Java tab UI copy: the "pack settings" the toggle selects are
**the instance's own saved settings**, not values shipped by the modpack author (which don't exist).

## 6. "Toggle-everything" Settings audit (enumerated candidates)

Implicit/absent on-off behaviors found in the current UI that should become explicit Settings toggles:

| # | Candidate toggle | Current state | Backing |
|---|------------------|---------------|---------|
| T1 | **Sidebar starts collapsed** | sidebar always expanded, no control | new (§4.3) |
| T2 | **Offline mode** (force offline identity) | `Settings.offline_mode` exists in Rust (settings.rs:35) but **not exposed in the UI** and missing from the `ipc.ts` Settings type | wire existing field |
| T3 | **Auto-download missing Java** | always auto-provisions Temurin silently (`ensure_java`) | new flag (gate provisioning) |
| T4 | **Confirm before deleting an instance** | delete confirmation is hardcoded (Home.tsx) | new flag |
| T5 | **Show console log panel by default** on launch | console auto-shows when running; no user control | new flag |

| T7 | **Maximize window on start** | `tauri.conf.json` hardcodes `maximized: true` | new flag (lower priority) |

T1 + T2 are the clear wins (T2 is "free" — the field exists). T3–T5 are genuine implicit behaviors.
T6/T7 are stretch. Final set is Q7 for the human.

## 7. Workstreams → branches + dependency ordering

Six workstreams. WS-A is the only hard prerequisite for the per-instance Java/Tech work; the sidebar
and Settings-audit streams are largely independent and can run in parallel.

```
WS-A (backend Java/RAM foundation) ──┬──► WS-D (Instance Detail: Java + Tech Info tabs)
                                     └──► (Settings UI per-instance hints)
WS-B (provider pack-info backend) ──────► WS-D (Info tab)
WS-C (sidebar collapse)            ── independent ──►
WS-E (Settings toggle-everything)  ── mostly independent (T2 needs bindings regen from WS-A or its own)
WS-F (Instance Detail shell: header + tab bar + Modlist relocation) ── needs WS-B/WS-A only for the
        Info/Java tab *content*; the shell + Modlist tab can land first with Info/Java as stubs
```

**Recommended ordering:** WS-A and WS-B (backend, parallel) → WS-F (UI shell + Modlist, can start once
A/B DTOs exist or with stubs) → WS-D (fills Info/Java/Tech tabs) → WS-C and WS-E anytime (independent).

**Branch vs phased-checkpoints — open question (Q8).** Two viable shapes:
- **Separate branches/worktrees per workstream** — max parallelism, but WS-D/WS-F both edit
  `InstanceDetail.tsx` heavily and WS-A/WS-E both touch `settings.rs` + regenerate `bindings.ts` →
  **merge conflicts on `bindings.ts` (generated) and InstanceDetail are likely.**
- **One long-lived `ui-overhaul` branch with sequenced checkpoints** — avoids the generated-file and
  InstanceDetail conflicts, at the cost of less parallelism.

Recommendation: **one integration branch `ui-overhaul`, with WS-A/WS-B/WS-C as the first independent
checkpoint clusters and WS-D/WS-F sequenced after** (they share `InstanceDetail.tsx`). `bindings.ts`
regeneration is centralized at the end of each backend checkpoint to avoid churn. Surfaced as Q8.

## 9. Rejected / deferred approaches

- **Storing recommended RAM/Java parsed from the modpack** — rejected: neither format carries it (§5).
  Modeled as an always-empty tier instead of pretending to read it.
- **Per-sidebar-click write to `settings.json`** — rejected for live collapse state (disk churn);
  localStorage for live state, Settings for the default (§4.3).
- **Reading provider pack description from local import metadata** — rejected: only a short `summary`
  is stored; the full body requires a live provider project fetch (§4.5/G4).
- **Forking InstanceDetail into per-tab files with duplicated header logic** — deferred in favor of a
  persistent header outside a nested `<Outlet>` (§4.4) to avoid header drift across tabs.
