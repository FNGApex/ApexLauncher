# modpack

## What it does

Imports a local modpack archive (Modrinth `.mrpack` slice A, CurseForge `.zip` slice B), installs a pack from Browse one-click including FTB (slice C), or updates/locks an installed pack (slice D). `core/modpack.rs` is a pure parse/plan module (no Tauri commands, no filesystem writes except `extract_overrides`). All executing commands (`import_mrpack`, `import_curseforge_zip`, `install_modpack`, `update_modpack`) enqueue a `TaskJob` into `TaskManager` and return the `u64` task id; the terminal result (e.g. `MrpackImportResult`, `CfImportResult`, `ModpackInstallResult`, `PackUpdateResult`) is attached to the task snapshot via `finish_done_with_result` and arrives on the `task://update` event. `set_pack_lock` remains synchronous (no task). `core/modpack.rs` also provides `remap_to_staging` + `promote_staging` shared by all six job types (`ImportMrpackJob`, `ImportCfZipJob`, `ImportFtbJob`, `UpdateModpackJob`, `ModAddJob`, `ModUpdateJob`). `refresh_pack_meta` Tauri command — throttled 24h update-check that calls `provider.get_pack_summary(project_id, file_id)` and writes `last_update_check`, `latest_version`, `latest_version_id` to the instance manifest; returns `PackMetaRefresh { update_available, latest_version, checked }`. **CF manual-download UX:** `CfManualFile { project_id, file_id, file_name, page_url, expected_sha1: Option<String>, size: Option<u64> }` is the output type for files that cannot be auto-downloaded; `impl From<&CfManualFile> for PendingManual` converts at import time. `cf_file_page_url(slug: Option<&str>, project_id: u64, file_id: u64) -> String` builds the exact file-page URL using the slug when available; `resolve_and_build_cf_plan` enriches each manual entry with a slug via `get_mod_slug`. **FTB planner:** `FtbPackPlan { downloads, manual, overrides }` mirrors `CfPackPlan`; `build_ftb_pack_plan(manifest, resolved_cf_files, mc_dir)` (pure) routes FTB-CDN files to downloads and CF-referenced files (already resolved) to downloads or manual; `resolve_and_build_ftb_plan(manifest, cf_client, mc_dir)` (async) calls `CurseForgeProvider::get_file` for each CF-referenced file then delegates to `build_ftb_pack_plan`; `ftb_dest_path(path, name)` normalizes the FTB file path+name into a relative dest path. FTB install populates `Source.recommended` from `FtbVersionManifest.specs.recommended` (activates tier-1 Java/RAM precedence). FTB update-apply is out of v1 scope; `update_modpack` returns an error for FTB without enqueueing a task.

## Coupling

- **download-runner domain** — all four pack job types (`ImportMrpackJob`, `ImportCfZipJob`, `ImportFtbJob`, `UpdateModpackJob`) enqueue into `TaskManager` and use `TaskContext` for lifecycle progression; `execute_plan_cancellable` (from `download.rs`) is the download step; `remap_to_staging`/`promote_staging` (defined here in `modpack.rs`) are shared with `ModAddJob`/`ModUpdateJob` in `lib.rs`; terminal results ride `task://update` via `finish_done_with_result`
- **instances domain** — `import_mrpack`/`import_curseforge_zip`/`update_modpack` job implementations call `instances::create`, `instances::load_manifest`, `instances::save_manifest`; `ModEntry` (defined in `instances.rs`, includes `from_pack: bool`) is the output shape all planners produce; `Instance.pack_locked` + `instances::ensure_not_locked`/`set_pack_lock` are in `instances.rs`
- **providers domain** — `resolve_and_build_cf_plan` calls `CurseForgeProvider::get_file` and depends on `ProviderHttpClient`/`ProviderError`/`VersionFile`; `resolve_pack_file` calls provider APIs; any change to those types or `cf_api_key_from` requires a matching update here
- **download domain** — both job implementations build a `DownloadPlan` and call `download::execute_plan_cancellable`/`build_client`; `ItemStatus`/`NoOpSink` come from `download.rs`
- **frontend-shell / IPC** — `MrpackImportResult`, `CfImportResult`, `CfManualFile`, `ModpackInstallResult`, `PackUpdateResult` are hand-mirrored in `src/lib/ipc.ts`; `importMrpack`/`importCurseforgeZip`/`installModpack`/`updateModpack` return `Promise<number>` (task id); FTB install reuses `installModpack` (same command, "ftb" provider) and returns the same `CfImportResult` shape; results arrive on `task://update` when `status.kind === "done"` and `task.result` is set; any Rust struct change requires a manual `ipc.ts` edit
- **mod-install domain** — `remap_to_staging`/`promote_staging` defined here are imported by `ModAddJob`/`ModUpdateJob` in `lib.rs` (`use core::modpack::{promote_staging, remap_to_staging}`)

## Conventions worth knowing

- Pure-planner / thin-executor split mirrors `mod_install.rs` and `resolver.rs`: all security-critical logic lives in unit-tested pure functions; the Tauri command only does I/O orchestration.
- `staging_dir_for(inst_dir, task_id)` → `<inst_dir>/.staging-<task_id>/`; task_id is the `u64` assigned at enqueue; staging dir is a sibling of the instance mods dir so `rename()` is same-filesystem and atomic.
- `remap_to_staging` rewrites only items whose `dest` falls under `mc_dir`; items outside `mc_dir` are passed through unchanged (e.g. items already pointing at cache).
- `promote_staging` is a recursive rename-walk; on success staging dir is left empty (caller removes it); on cancel/fail caller calls `remove_dir_all` on the staging dir.
- `plan_pack_update` is a pure diff: given `current_mods` and `new_plan_entries`, partitions entries by `from_pack` flag and filename collision. User-added mods (`from_pack=false`) survive unless their filename is overridden by a new pack entry.
- mrpack download host allowlist (`ALLOWED_HOSTS`): `cdn.modrinth.com`, `github.com`, `raw.githubusercontent.com`, `gitlab.com` — a `downloads[]` URL outside this list aborts the whole import via `ModpackError::DisallowedHost`.
- `validate_relative_path` rejects absolute paths, `\`-prefixed paths, Windows drive-letter prefixes, and any `..` component.
- CF hash preference in `build_cf_pack_plan`: only `sha1` is checked — a resolved file with only an md5 hash routes to `manual`.
- `CfManualFile.page_url` is built by `cf_file_page_url(slug, project_id, file_id)`. When slug is available (fetched via `get_mod_slug`), it produces `https://www.curseforge.com/minecraft/mc-mods/<slug>/files/<file_id>` (exact file page). Fallback (slug fetch fails or slug absent) is the numeric-id project URL `https://www.curseforge.com/projects/<project_id>`. The previously-tracked follow-up `modpack-import-cf-manual-slug-link` is now resolved.
- `impl From<&CfManualFile> for PendingManual` is the only conversion path; both `expected_sha1` and `size` are `Option` so they propagate as-is from the CF API response.
- No rollback on partial failure: a half-populated instance may be left on disk — tracked follow-up `modpack-import-partial-cleanup`.
- `src-tauri/tests/curseforge_live.rs` is a `#[ignore]`d integration test hitting the real CF API; reads the key from a gitignored `.env`.
- FTB file routing: `FtbFile.url` non-empty → FTB-CDN download (direct URL, sha1 verified); `FtbFile.curseforge` set + `url` empty → CF-referenced (`FtbCurseforge { project, file }` resolved via `CurseForgeProvider::get_file`); resolved CF files with sha1 → downloads list, without sha1 → manual list (same `CfManualFile` / `pending_manual` pipeline as CF .zip).
- `ftb_dest_path(path, name)` joins path + name, strips a leading `/mods/` prefix if present (FTB API emits paths like `/mods/foo.jar`), returns the relative dest string.
- FTB update-apply deferred to v2: `update_modpack` for "ftb" returns an error string immediately. Update-check (`refresh_pack_meta`) still works for FTB and will surface update-available in the InfoTab banner.
- `Source.recommended` (type `Option<u64>` in MB) is populated from `FtbVersionManifest.specs.recommended` at install time; this activates the previously-dormant tier-1 Java/RAM precedence in `java_resolve::resolve_effective_java`.
